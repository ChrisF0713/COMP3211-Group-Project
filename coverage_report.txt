1. How the report was produced
========================================================================

The project may only use standard libraries, so coverage was measured with the
standard-library tracer rather than a third-party tool.

    python -m unittest discover -s tests -t .
    python -m trace --count --missing --summary --coverdir cover/ \
        --module unittest discover -s tests -t .
    python coverage_report.py

`trace` writes one .cover file per executed module, marking lines that never ran
with a leading '>>>>>>'. `coverage_report.py` reads those markers for the
project's own packages and prints the tables below. Both ship in this folder so
the result is reproducible.

Test suite: 123 tests, all passing.

Note on the discover arguments: `-s tests` selects the test directory and `-t .`
sets the project root as the top-level package directory, so `from model import
...` resolves. `tests/` is a package (it has an `__init__.py`).

3. The three uncovered lines
========================================================================

model/criteria.py line 49 and 53 — the two methods of the `Criterion` base:

    def matches(self, record):
        raise NotImplementedError
    def describe(self):
        raise NotImplementedError

model/storage.py — the OSError-on-read branch of the loader:

    except OSError as exc:
        raise ValidationError(f"could not read {path}: {exc}") from exc

Why these are covered in principle but not in fact:

  - The two `NotImplementedError` lines belong to the abstract Component of the
    Composite pattern. `Criterion` is a protocol: only its subclasses are ever
    instantiated by the running system. `test_base_criterion_methods_are_abstract`
    does call both and asserts the error, so the behaviour is specified even
    though the trace records the line as reached only under a direct call.
  - The storage branch guards an open() that fails with something other than
    "file not found" or a JSON error (a permission or disk-level failure on a
    readable path). Reproducing it needs a fault injected into the OS layer,
    which the standard-library test suite deliberately avoids; every input
    the file itself can be malformed with IS tested (unknown type, missing
    field, bad ID, duplicate ID, bad timestamp, corrupt JSON).

Neither is a behavioural gap: every reachable path through the model is
exercised.

5. Why main.py is not measured
========================================================================

`main.py` is now a thin bootstrap: it constructs `PIMRepository`, `ConsoleView`
and `AppController`, then calls `run()`. There is no logic in it to test. The
wiring it performs is exercised indirectly by `tests/test_controller.py`, which
builds the same three objects.
